
# Проверочный лист безопасности PropDevelopment (по шаблону)

## I. Управление доступом

Раздел включён, так как в компании отсутствует централизованная система управления доступом. 
У каждого приложения собственная логика аутентификации, нет разграничения прав, не контролируется передача прав между сотрудниками, 
и отсутствует аудит доступа. Эти нарушения создают риски утечек и ошибок, в том числе случаев отображения данных одного клиента другому.

| № | Вопрос                                                                                             | Да/нет   | Комментарий                                                                                                |
|---|----------------------------------------------------------------------------------------------------|----------|------------------------------------------------------------------------------------------------------------|
| 1 | Используется ли многофакторная аутентификация (MFA) для доступа к критическим системам и сервисам? | нет      | MFA не упоминается, скорее всего не реализована. Рекомендуется к внедрению для доступа в CRM и финсистемы. |
| 2 | Проводится ли аудит и пересмотр учётных записей с повышенными привилегиями на регулярной основе?   | нет      | Нет упоминаний об аудите учётных записей. Необходимо ввести контроль и журналирование действий.            |
| 3 | Реализован ли принцип минимальных привилегий при назначении ролей и прав доступа?                  | нет      | В системах нет разграничения доступа, особенно в API. Принцип минимум привилегий нарушен.                  |
| 4 | Ведётся ли журналирование всех операций доступа к системам и данным? Кто имеет доступ к журналам?  | нет      | Централизованное журналирование отсутствует. Необходимо внедрить ELK или аналогичную систему.              |
| 5 | Используются ли системы аутентификации пользователей для доступа к системам?                       | частично | Нет централизованной системы, у каждого приложения своя.                                                   |
| 6 | Ограничен ли доступ к системам из внешних источников?                                              | частично | Доступ к API ограничивается только firewall. Нужна авторизация и аудит доступа.                            |

## II. Безопасность данных

Компания обрабатывает персональные и чувствительные данные (ФИО, паспортные данные, сделки, платежи), 
но отсутствует шифрование, классификация и контроль доступа к этим данным. Резервные копии хранятся в ЦОД без защиты. 
Это нарушает 152-ФЗ и мешает развитию аналитических и ML-сервисов.

| № | Вопрос                                                                                                                              | Да/нет   | Комментарий                                                                       |
|---|-------------------------------------------------------------------------------------------------------------------------------------|----------|-----------------------------------------------------------------------------------|
| 1 | Разработана ли политика классификации данных, и актуализируется ли она в соответствии с действующим законодательством?              | нет      | Классификация отсутствует, данные не размечены, нет уровней доступа.              |
| 2 | Используется ли шифрование на уровне базы данных, файловой системы и при передаче данных по сети?                                   | нет      | Шифрование не упоминается. Важно включить TLS, Transparent Data Encryption и VPN. |
| 3 | Проводится ли регулярное резервное копирование данных? Хранятся ли резервные копии в защищённых хранилищах?                         | частично | Бэкапы есть, но хранятся внутри ЦОДа. Не зашифрованы и не изолированы.            |
| 4 | Ведётся ли учёт персональных данных, и применяются ли специальные процедуры обработки и хранения для различных типов данных?        | нет      | Учет не ведётся, методы хранения одинаковы для всех данных. Это нарушение 152-ФЗ. |
| 5 | Осуществляется ли мониторинг доступа к данным на основе их классификации? Используются ли метки безопасности для маркировки данных? | нет      | Нет классификации, следовательно, нет контроля. Требуется внедрение DLP.          |
| 6 | Реализованы ли системы или процессы контроля сохранности данных?                                                                    | нет      | Потеря или искажение возможны, особенно при интеграциях.                          |

## III. Интеграции и API

Одно из самых уязвимых мест системы — взаимодействие с API внешних партнёров. 
Нет политик безопасности, авторизации и ограничений прав доступа. Внешние системы могут получить данные, к которым не должны иметь доступ. 
Это угрожает конфиденциальности данных клиентов и нарушает требования 152-ФЗ.

| № | Вопрос                                                                                      | Да/нет | Комментарий                                              |
|---|---------------------------------------------------------------------------------------------|--------|----------------------------------------------------------|
| 1 | Применяются ли политики ограничения доступа к API (например, на уровне IP, tenantId, auth)? | нет    | Только firewall. Необходимо внедрить API Gateway.        |
| 2 | Используется ли авторизация по токенам (например, OAuth2, JWT)?                             | нет    | Не реализована. Доступ открытый и без валидации клиента. |
| 3 | Ведётся ли аудит использования API (метрики, логирование, частота, ошибки)?                 | нет    | Нет системной телеметрии.                                |
